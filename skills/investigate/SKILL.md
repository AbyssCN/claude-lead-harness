# /investigate — 系统化根因调试

> **铁律:无根因不修。** 修症状 = 打地鼠。找到根因再动手,诊断阶段禁提修复方案。

纯方法论 skill(不封特定 MCP 工具,用 runtime 原生 Grep/Read/git;需并行跑多假设时可派多个子 agent)。

> **先有红命令,才许提假设。** 报告写成文件 `<仓根>/docs/investigations/<YYYY-MM-DD>-<slug>.md`,**第一节固定是 `## 0 · 红命令`**:
> 一个代码块,第一行 `$ <实际跑过的命令>`,接着贴输出的关键几行,最后一行 `→ exit <非 0 退出码>`(或失败断言原文)。
> 这条命令必须是本次真跑过、能确定性复现症状的;跑不出红 = 还没复现,回 Phase 2,不进 Phase 4。
> 修完在 Phase 5 用**同一条命令**跑出 `→ exit 0`,贴在报告末节。机械检查:
> `awk '/^## /{n++} n==1' <报告> | rg -q '^\$ ' && awk '/^## /{n++} n==1' <报告> | rg -q '→ exit [1-9]'`。

## Phase 1 — 历史搜索(先查后调)
同一消息并行发:`git log --oneline -20 -- <相关文件>`(近期变更)+ Grep 既有 `docs/plan/`·NOTES·error 记录搜错误关键词(有先例走 /omd-recall 先召回)。命中已知修复 → 直接引用,跳到修复。

## Phase 2 — 复现
建一条能确定性触发症状的回路,按这个先后取第一个用得上的:失败测试 → curl → CLI 对快照 → 浏览器脚本 → 回放 → 二分 → 新旧版对比。回路要秒级、每次结果相同;偶发的先把复现率提上去(循环 · 加压 · 固定种子)再往下走。产出就是报告的「0 · 红命令」一节:一条可重跑的命令 + 非 0 退出码。建不出回路 → 写清缺什么环境,别猜。

## Phase 3 — Scope Lock
从症状追到最窄受影响目录,声明范围;此后 Edit 只在范围内。危险信号立即停:「顺手修个相关的」(不顺手,记 follow-up)、「既然在改不如重构」(不重构,本 bug 修完再评估)。

## Phase 4 — 模式匹配 + 假设验证(最多 3 个)
先 step-back 自问:这类症状(数据不一致/超时/类型错/竞态/权限泄漏/schema 漂移)在本技术栈通常由哪层引起?建宏观诊断框架再缩范围,别直接跳到最"像"的模式。**同文件反复修 bug = 架构问题,不是巧合**。

每假设三步推导:**观察**(引 file:line 我看到什么)→ **推论**(若成立还应看到什么)→ **验证**(设计能区分成立/不成立的实验)。追踪表标 CONFIRMED/REJECTED。先验证再修(可疑根因处加临时 log/断言,跑复现看证据是否吻合)。**先验前提**:同一道检查上两次修复都没过,或 3 个假设全败 → 不修第三次、不全套重跑;写下这几次共同依赖的前提(数据真是这样?跑的真是这份代码?检查量的真是这件事?),直接验证它。危险信号:还没追数据流就提修复 = 在猜。

## Phase 5 — 修复 + 验证
根因确认后最小改动:最少文件、最少行,不顺手重构相邻代码。写回归测试(不修 FAIL、修后 PASS),跑测试套件贴输出。复现原始场景确认已修 + 跑变更相关验证。不说"应该能修好",验证并证明。

## Phase 6 — 报告 + 扫同类
报告(写在上面的文件里,首节红命令):症状 / 根因(为什么)/ 模式 / 修复(file:line)/ 证据 / 回归测试 / 状态(DONE · DONE_WITH_CONCERNS · BLOCKED)。**修完扫一片**:用根因反推同类——Grep 同 pattern(根因是"缺 scope 过滤" → 全仓找所有 db 访问点;"未校验入参" → 找所有 untrusted 入口)。>5 处别一次全修,修 1-2 关键,其余记 NOTES 留 follow-up。
